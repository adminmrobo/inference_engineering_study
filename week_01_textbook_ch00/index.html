추론이란 무엇인가

GPU를 사서 모델을 올리면 끝일까? 왜 생성 AI의 추론에는 '세 층'이 필요할까?

0장은 이 책 전체의 지도입니다. 모델의 일생을 학습과 추론 두 단계로 나누고, 생성 AI의 추론을 잘하려면 런타임 · 인프라 · 도구 세 층이 함께 맞물려야 한다고 말합니다. 그리고 1장부터 7장까지가 이 지도의 어디에 놓이는지 보여 줍니다.

교재: Kiely, P. (2026). Inference Engineering, Chapter 0. Baseten Books. 그림 0.1~0.3.

1칸

두 단계 — 학습과 추론

모델: 생성 AI 모델의 일생교재: 0장 첫머리

연구실에서는

새 시약을 개발하는 건 한 번이지만, 그 시약을 써서 실험하는 일은 매일 수백 번 일어납니다. 개발실과 실험실은 다른 기술이 필요해요.

모델에서는

학습은 데이터에서 가중치를 배우는 과정이고, 추론은 그 모델을 실제 서비스로 돌리는 과정이에요 원문. 학습은 몇 번, 추론은 요청마다 일어납니다.

학습은 한 번, 추론은 요청마다

10000
30일
모델

풀이

  1. 지난 10년의 머신러닝 붐에서 많은 데이터 과학자가 학습부터 추론까지 다 해 봤어요. 고전 머신러닝의 추론은 비교적 단순했어요.
  2. 교재 저자의 회사도 초기에는 XGBoost 같은 모델을 가벼운 CPU와 단순한 소프트웨어로 돌렸다고 합니다.
  3. 생성 AI는 다릅니다. 가중치를 받고 GPU를 사도, 큰 규모의 서비스에 맞게 빠르고 안정적이지 않아요. 그래서 세 층이 필요해요.

이 칸의 한계: "학습은 한 번"은 단순화예요. 실제로는 미세조정·재학습이 반복됩니다. 하지만 추론이 요청마다 쌓인다는 점은 그대로예요.

생성 AI로 치면

챗봇에 질문 하나를 보내면 그때마다 추론이 한 번 돌아요. 사용자가 많을수록 추론 비용이 학습 비용을 금세 넘어설 수 있어요.

비유의 한계: 정확한 비율은 모델·사용량마다 다릅니다.

현장에 옮기면

공장의 금형(학습)은 한 번 만들지만 사출(추론)은 제품마다 반복됩니다. 사출 공정의 효율이 원가를 정해요.

비유의 한계: 금형과 달리 모델은 같은 입력에도 매번 계산이 필요합니다.

초파리 연구원

그러니까 "모델을 만든다"와 "모델을 서비스한다"는 다른 일이라는 거지. 둘째가 이 책이고.

2칸

런타임 층 — 여섯 가지 모델 성능 기법

모델: 런타임 최적화교재: 그림 0.2

연구실에서는

실험대 하나를 잘 쓰는 요령이 여러 가지 있어요: 시료를 모아서 한 번에(배칭), 쓴 시약 재사용(캐싱), 덜 정밀한 저울로 충분할 땐 그걸로(양자화)…

모델에서는

런타임 층은 쿠다 → 파이토치 → vLLM·SGLang·TensorRT-LLM 같은 추론 엔진 위에서, 배칭·캐싱·양자화·추측·병렬화·분리 여섯 기법을 씁니다 원문. 플래시어텐션 같은 커널도 큰 성능 차이를 냅니다.

기법 카드 — 무엇을 줄이고 무엇을 늘리나

기법

그림 0.2 따라 하기 — 추측 디코딩

0.7
4개
한 번 검증에 나오는 토큰 수 (기댓값) = (1 − ak+1) / (1 − a)  ·  a = 적중률, k = 초안 개수

풀이

  1. 보통 디코딩은 큰 모델을 한 번 돌릴 때(순전파 한 번) 토큰을 하나 냅니다.
  2. 추측 디코딩은 작은 쪽이 초안 토큰 여러 개를 먼저 쓰고, 큰 모델이 한 번에 검증해요. 맞은 데까지 받아들이고 틀린 곳부터 버립니다(그림 0.2의 "tel·le·vis·ion" → "tel·le·scope").
  3. 초안이 잘 맞으면 한 번에 여러 토큰이 나와서 지연시간이 줄어요. 자세한 방법은 5장 5.2절이에요.

이 칸의 한계: 기법 여섯 개는 서로 겹치기도 하고 부딪치기도 해요. "다 켜면 여섯 배"가 아닙니다. 그리고 한 대가 아무리 빨라도 트래픽은 결국 넘칩니다 → ③ 칸.

생성 AI로 치면

챗봇의 답이 "타다닥" 빠르게 나오는 데에는 배칭·캐싱·추측 같은 런타임 기법이 숨어 있어요. 이미지·음성·영상 모델에도 같은 기법들이 쓰입니다.

비유의 한계: 모델 종류마다 맞는 기법이 달라요(6장).

현장에 옮기면

반복되는 서식 문서를 처리할 때 앞부분이 같으면 캐싱 효과가 큽니다.

비유의 한계: 문서마다 앞부분이 다 다르면 캐싱 이득이 작아요.

기댓값 식은 어디서 왔나

초안 k개가 각각 확률 a로 맞고, 처음 틀린 곳에서 멈춘다고 하면, 한 번 검증에서 얻는 토큰 수의 기댓값은 1 + a + a² + … + ak = (1 − ak+1)/(1 − a) 입니다(마지막 1개는 큰 모델이 직접 내는 토큰). 추측 디코딩 연구에서 흔히 쓰는 단순화이고, 교재 0장에는 이 식이 없습니다. 이 페이지에서는 설명용으로 씁니다.

주판봇

적중률 0.7, 초안 4개면 한 번에 2.8개쯤? 그럼 거의 세 배잖아! …아, 검증하는 데도 시간이 드는구나.

3칸

인프라 층 — 자동 확장에서 하나의 풀까지

모델: 추론 인프라교재: 그림 0.3

연구실에서는

실험실이 세 건물에 흩어져 있으면, 한 건물은 줄이 길고 다른 건물 실험대는 비어 있기도 해요. 예약을 하나로 합치면 빈자리를 바로 씁니다.

모델에서는

처음엔 자동 확장(언제 복제본을 늘리고 줄이나), 몇백 GPU를 넘으면 용량(GPU를 충분히 구하기)이 문제가 됩니다. 여러 지역·여러 클라우드로 퍼지면 사일로가 생기고, 마지막 단계는 모든 자원을 하나의 풀로 다루는 전 지구적 시스템이에요 원문.

사일로 vs 하나의 풀

방식
0.6

풀이

  1. 런타임을 아무리 최적화해도, 서버 한 대는 언젠가 감당 못 할 트래픽을 받습니다. 교재는 이것을 "쿠다나 파이토치 문제가 아니라 시스템 문제"라고 말해요.
  2. 규모가 커질수록 문제의 성격이 바뀝니다: 자동 확장 → 용량 → 사일로 → 하나의 풀.
  3. 여러 클라우드에 걸친 인프라는 가동률도 높여요(한 지역·한 클라우드가 멈춰도 버팀). 사용자 가까이에서 돌리면 전체 지연시간도 줄어요.

이 칸의 한계: 하나의 풀은 강력하지만 만들기 어렵습니다. 그리고 아무리 좋은 인프라도 엔지니어가 쓰기 어려우면 소용없어요 → ④ 칸.

생성 AI로 치면

전 세계 사용자가 쓰는 챗봇은 미국·유럽·아시아의 GPU를 묶어 씁니다. 사용자 가까운 곳에서 답하면 더 빨라요.

비유의 한계: 데이터를 어느 나라에서 처리해도 되는지(1장 규제)가 풀을 제한할 수 있어요.

현장에 옮기면

콜센터의 지역별 상담원을 하나의 대기열로 묶는 것과 비슷해요.

비유의 한계: 상담원과 달리 GPU는 모델을 미리 올려 둬야 해서 옮기는 데 시간이 걸립니다(7장 콜드 스타트).

인턴 모아

사일로에서 버린 요청이 풀에서는 남은 칸으로 갔어요. 같은 GPU 수인데도요!

4칸

도구 층 — 블랙박스와 부품 사이

모델: 개발자 경험교재: 0장 후반

연구실에서는

버튼 하나로 끝나는 자동 분석기는 편하지만 조건을 못 바꾸고, 부품만 잔뜩 있는 실험대는 뭐든 되지만 하루 종일 조립해야 해요.

모델에서는

한쪽 끝은 블랙박스(가중치를 주면 API가 나옴), 다른 끝은 컴퓨트·네트워크·디스크 같은 기본 부품만 주는 것. 알맞은 개발자 경험은 그 사이 어딘가라고 교재는 말합니다 원문.

추상화 손잡이

50

풀이

  1. 통제력이 너무 적으면 중요한 서비스를 믿고 맡길 수 없어요.
  2. 추상화가 너무 낮으면 매번 바닥부터 만들어 생산성이 떨어져요.
  3. 그래서 추론 플랫폼을 만드는 쪽(외부 업체든 사내 팀이든)은 도구·개발자 경험을 세 번째 층으로 함께 설계해야 합니다.

이 칸의 한계: "알맞은 지점"은 팀과 서비스마다 다르고, 교재도 이것을 주관적이라고 말합니다. 그래프의 가운데 표시는 설명용이에요.

조수(하루)

손잡이 50 근처에서 두 막대의 합이 가장 커요. 하지만 이 곡선 자체가 설명용이라, 실제 지점은 팀이 정해요.

장

풀이
