    워크스테이션 GPU랑 개인용 GPU는 뭐가 달라요?

    조수(하루)

    교재 기준으로는 쓰임새예요. 워크스테이션은 전문 작업용 데스크톱 GPU(RTX Pro 6000), 개인용은 일상용 데스크톱 GPU(RTX 5090). 둘 다 "한 장짜리"라는 점이 데이터센터 GPU와 달라요.

    2칸

    연산 — 계산 공방(SM)과 행렬 프레스(텐서 코어)

    교재: 3.1.1 Compute그림 3.1

    그림 3.1 다시 그리기 · 곱하고 더하기 (MMA)

    텐서 코어가 하는 일은 D = (A × B) + C. "더하기(accumulate)"는 곱한 결과를 바탕 행렬 C에 얹는 것이에요. 단추를 누르면 D의 칸이 하나씩 채워집니다.

    공장에서는

    CPU는 복잡한 일을 순서대로 척척 해내는 장인 몇 명, GPU는 같은 동작을 수천 개 재료에 한꺼번에 하는 프레스 수천 대예요.

    GPU에서는

    GPU 안에는 SM(계산 공방)이 여럿, SM마다 코어가 여럿. 코어는 세 종류 — CUDA 코어(숫자 하나), 텐서 코어(행렬·벡터), SFU(sin · cos · log). 추론 계산력은 텐서 코어 기준으로 잽니다 원문.

    계산력 계기판 — 정밀도와 희소성을 바꿔 보기

    정밀도
    희소성 (2:4)

    풀이

    1. 스레드는 CPU와 GPU에서 뜻이 비슷해요. CPU는 수십~수백 개, GPU는 수만~수십만 개가 한 클럭에 일을 바꿔 가며 단순한 명령을 동시에 실행합니다.
    2. 계산력 단위는 FLOPS(1초에 하는 부동소수점 연산 수). 데이터센터 GPU는 테라(1012)~페타(1015) FLOPS.
    3. 사양표에는 밀집과 희소 두 값이 있어요. 희소 값은 0이 절반인 2:4 구조에서 0 곱하기를 건너뛴 값이라 보통 두 배(항상은 아님). 추론은 기본이 밀집이니 밀집 값을 보세요.
    4. 정밀도를 반으로 줄이면 FLOPS는 대체로 두 배. 그래서 GPU를 비교할 땐 같은 정밀도끼리 비교해야 해요.
    5. 계산력이 병목인 일: LLM 프리필, 이미지·영상 생성. 이런 일이 주력이면 FLOPS 큰 가속기를 고릅니다.

    이 칸의 한계: FP16·FP4·희소 막대는 교재 규칙(정밀도 반 → 2배, 희소 → 보통 2배)으로 계산한 값이라 실제 사양표와 조금 다를 수 있어요. FP4는 블랙웰부터라 호퍼·러브레이스 칸은 "지원 안 함"으로 둡니다.

    주판봇

    FP16에서 FP8로 바꾸면 막대가 두 배! …근데 교재가 5.1절에서 "그대로 두 배 성능은 아니다"라고 했지.

    L2 캐시 — 모든 SM이 함께 씀 (H100 50 MB)
    VRAM (HBM) — 칩 밖의 큰 창고 · 수십~수백 GB · 대역폭 = 이 창고에서 캐시로 데이터를 실어 오는 속도

    보라 칸 = 텐서 코어(TC), 파란 칸 = SM 안의 L1(공유 메모리). L0는 텐서 코어 하나의 명령 캐시라 그림에선 생략했어요.

    공장에서는

    기계실 바깥에 커다란 창고(VRAM)가 있고, 공방마다 손 닿는 선반(L1), 공방들이 함께 쓰는 중간 선반(L2)이 있어요. 창고는 크지만 멀고, 선반은 작지만 가까워요.

    GPU에서는

    VRAM은 DRAM(칩 밖, 기가바이트 단위)이고 HBM3 · HBM3e · HBM4로 붙어 있어요. 캐시는 SRAM(칩 안, 킬로~메가바이트, 더 빠르고 비쌈). H100: SM마다 L1 256 KB, 칩 전체 L2 50 MB 원문.

    모델이 들어갈까? — VRAM 계산기

    70B
    숫자 하나의 크기
    GPU
    몇 장

    풀이

    1. VRAM 총량이 올릴 수 있는 모델 크기를 정해요. 교재의 경험칙: 모델 무게 + 최소 50% 여유(KV 캐시용). 긴 문맥 · 큰 배치 · 영상 생성 모델은 더 많이.
    2. 무게도 안 들어가면 모델을 올리다 OOM(메모리 부족)으로 실패. 여유가 모자라면 추론이 느려지거나 OOM으로 죽어요.
    3. 모델 무게 ≈ 파라미터 수 × 숫자 하나의 바이트. 70B × 2바이트 = 140 GB → H100 한 장(80 GB)에는 안 들어가요.
    4. 메모리 대역폭은 낮~중간 배치 LLM 디코드의 병목이에요. 토큰을 더 빨리 뽑고 싶다면 대역폭 큰 가속기(H100 대신 H200)를 고릅니다.

    이 칸의 한계: 무게 계산은 파라미터 × 바이트만 셌어요. 실제로는 활성값 · 엔진 작업 공간 · 여러 장으로 나눌 때의 중복이 더 들어갑니다. 여러 장 합산은 7칸(NVLink)처럼 잘 이어져 있을 때 이야기예요.

    생성 AI로 치면

    챗봇 서비스로 치면 VRAM은 "모델 + 지금 대화 중인 모든 손님의 대화 기록(KV 캐시)"을 담는 그릇이에요. 손님이 늘수록 여유분이 빨리 줄어요.

    비유의 한계: KV 캐시 크기는 문맥 길이 · 배치 · 모델 구조에 따라 크게 달라요.

    현장에 옮기면

    공장 창고 계획과 같아요. 기계(무게)만 들어간다고 끝이 아니라, 하루 작업 재료(KV 캐시)를 쌓을 자리가 있어야 라인이 돌아요.

    비유의 한계: 창고는 넓힐 수 있지만 GPU 메모리는 장을 늘려야만 늘어요.

    인턴 모아

    70B를 16비트로 올리려면 무게만 140 GB, 여유까지 210 GB… H100으론 세 장 이상이네요. 기록해 둘게요.

    4칸

    어느 숫자를 볼까 — 프리필은 FLOPS, 디코드는 대역폭

    교재: 3.1.1 · 3.1.2 결론3주차 2.4절 복습

    공장에서는

    주문서 한 장을 통째로 읽어 들이는 일(프리필)은 프레스 힘이, 제품을 하나씩 찍어 내보내는 일(디코드)은 창고에서 재료를 실어 오는 속도가 좌우해요.

    GPU에서는

    교재: 계산력은 LLM 프리필 · 이미지·영상 생성의 병목, 메모리 대역폭은 낮~중간 배치 LLM 디코드의 병목. H100과 H200은 FP8 계산력이 같지만(1,979 TF) 대역폭은 3.35 → 4.8 TB/s 원문.

    두 일의 속도 상한 비교 (설명용 근사)

    모델 (FP8 무게)
    8000토큰
    보기

    풀이

    1. 배치 1 디코드: 토큰 하나를 만들 때마다 모델 무게를 창고에서 한 번 다 읽어야 해요. 그래서 초당 토큰 상한 ≈ 대역폭 ÷ 무게 바이트.
    2. 프리필: 입력 토큰 N개를 한꺼번에 계산해요. 토큰 하나에 파라미터마다 곱하기·더하기 2번이라 계산량 ≈ 2 × 파라미터 × N, 시간 하한 ≈ 계산량 ÷ FLOPS.
    3. 그래서 H100 → H200: 디코드 상한은 약 1.43배(4.8 ÷ 3.35), 프리필 하한은 그대로(계산력이 같으니까).
    4. 이 두 줄을 그래프 하나로 그린 것이 이번 주 논문 루프라인 모델이에요.

    길

    풀이

    1. 데스크톱: 고급 소비자 GPU 한두 장 달린 PC도 있지만, 데스크톱 추론의 선두는 점점 Apple이에요. M 시리즈는 CPU와 GPU가 통합 메모리 하나를 같이 써서, GPU가 훨씬 큰 메모리에 접근해요(대신 느림).
    2. 교재 표: RTX 5090 32 GB · 1,792 GB/s · 컴퓨터 $5,000 vs M3 Ultra 512 GB · 819 GB/s · $10,000. 용량과 속도의 맞바꿈이 중급 가격대까지 이어져요. 크롬북 같은 저가 기기는 의미 있는 로컬 추론이 어려워요.
    3. Ollama · llama.cpp로 100B+ 모델을 강하게 양자화해 고급 개인 하드웨어에서 돌릴 수 있어요. MoE는 요청 하나가 전체 무게의 일부만 건드려 데스크톱에 유리해요. 이미지 생성은 ComfyUI, 브라우저는 WebLLM.
    4. 모바일: 온디바이스 작업의 대부분. Android는 AI Edge SDK · ML Kit GenAI(Gemini Nano, Gemma), iOS는 Foundation Models · Core ML. 고급 폰도 1~2B 파라미터를 넘으면 버거워요. 받아쓰기 · 음성 합성 · 번역처럼 작은 모델로 되는 일이 잘 맞아요.
    5. 결론: 로컬이냐 클라우드냐가 아니라 둘 다. 작은 모델 · 빠른 질의는 기기에서, 무거운 일은 데이터센터에서.

    이 칸의 한계: 토큰 속도 상한 = 대역폭 ÷ (한 토큰에 읽는 무게)로 계산한 설명용이에요. MoE는 전체 무게가 메모리에 다 있어야 하지만 토큰당 읽는 양은 활성 부분만이라고 근사했어요. 열 · 배터리 · 소프트웨어 효율은 뺐습니다. 일반 사용자는 최신 기기를 갖고 있지 않다는 점도 기억하세요.

    다시다시

    다시 읽기 — GPU를 고르는 질문 다섯

    3장 정리

    ① 들어가는가? (VRAM)

    무게 + 50% 여유. 안 되면 장을 늘리거나 양자화(6주차 5.1).

    한계: KV 캐시는 문맥·배치 따라 더 필요.

    ② 무슨 일이 많은가?

    프리필 · 이미지 · 영상 → FLOPS. 디코드(낮~중간 배치) → 대역폭.

    한계: 배치가 크면 디코드도 계산 쪽으로 간다 (논문편).

    ③ 같은 정밀도로 비교했나?

    FP8끼리, 밀집끼리. 희소 값에 속지 않기.

    한계: 정밀도를 낮추면 품질 확인이 필요.

    ④ 길은 충분한가?

    여러 장이면 NVLink · NVSwitch, 노드 사이면 InfiniBand(비트 단위!).

    한계: 클라우드마다 구성이 다르다.

    ⑤ 너무 크지 않은가?

    작은 모델은 MIG 조각, 기기에서 될 일은 로컬로.

    한계: MIG는 일부 GPU만, 로컬은 기기가 제각각.

    디코드 상한 ≈ 대역폭 ÷ 무게 바이트  ·  프리필 하한 ≈ 2 × 파라미터 × 토큰 ÷ FLOPS  ·  필요 VRAM ≈ 무게 × 1.5
