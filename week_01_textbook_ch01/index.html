    최적화는 균형 — 다섯 가지 알아 둘 것

    모델: 지연시간·처리량·품질의 균형교재: 1장 도입, 그림 1.1

    연구실에서는

    실험 장비를 고를 때 "제일 좋은 것"은 없어요. 시료가 몇 개인지, 얼마나 정밀해야 하는지, 예산이 얼마인지가 정해져야 고를 수 있어요.

    모델에서는

    많은 성능 개선은 지연시간·처리량·품질 사이의 거래에서 나옵니다. 그래서 한 가지를 끝까지 올리기보다 알맞은 균형을 찾는 일이 많아요. 제약을 많이 알수록 결과가 좋아집니다 원문.

    알고 있는 것에 체크해 보세요

    풀이

    1. 다섯 가지: 모델 요구사항, 애플리케이션 인터페이스, 지연시간 예산, 단위 경제학, 사용 패턴.
    2. 제품 초기에는 이 답들이 흐릿합니다. 그때는 기성 API를 쓰는 편이 대개 낫다고 교재는 말해요.
    3. 제품이 커지고 요구사항이 또렷해지면, 그때 추론 엔지니어링이 할 만한 일이 됩니다.

    이 칸의 한계: 과녁 그림은 "아는 만큼 좁혀진다"는 생각을 보여 주는 설명용이에요. 다섯 가지 중 무엇이 먼저 정해지는지는 제품마다 다릅니다.

    주판봇

    "제일 좋은 것"이 없다니… 그럼 가장 비싼 걸 사도 소용없을 때가 있다는 거네.

    2칸

    1.1 공유 추론과 전용 배포

    모델: 과금 방식교재: 1.1, 표

    연구실에서는

    분석을 외부에 맡기면 건당 돈을 내고, 장비를 들이면 시간당 비용이 나가요. 시료가 적을 땐 외부, 많아지면 장비가 이득입니다.

    모델에서는

    공유 추론은 공개 API에 보내고 백만 토큰당 돈을 내요. 전용 배포는 GPU를 빌려 우리만의 서비스를 두고 GPU 시간당 돈을 냅니다 원문. 공유 vs 전용은 닫힌 vs 열린 모델과 꼭 같은 얘기는 아니에요.

    풀이

    1. 대부분의 AI 제품은 토큰당 과금 API로 시작해요. 제품-시장 적합성을 찾는 동안은 그게 맞는 거래예요.
    2. 전용 배포로 옮길 세 가지 이유: 규모(GPU당 내는 게 더 싸질 만큼 트래픽이 많음), 특화(맞춤 모델, 지연시간·가동률 요구), 오케스트레이션(여러 모델·여러 단계 파이프라인).
    3. 전용으로 가면 유연성과 통제력을 얻지만, 엔지니어링 부담이 늘고 월 지출의 바닥이 올라가요. 분명하고 당장의 사업상 필요가 있을 때만 옮기라고 교재는 말합니다.

    이 칸의 한계: 계산기는 GPU를 늘 꽉 채워 쓴다고 가정했어요. 실제로는 트래픽이 들쭉날쭉해 GPU가 노는 시간이 생기고(7장 자동 확장), 엔지니어 인건비도 빠져 있어요.

    생성 AI로 치면

    사내 문서 요약 봇이 하루 수천 건이면 API, 수백만 건이면 전용 배포를 검토하는 식이에요.

    비유의 한계: 어느 쪽이 싼지는 단가와 처리량 가정에 크게 달려요.

    현장에 옮기면

    전력 요금의 기본요금(전용)과 사용량 요금(공유)을 비교하는 것과 비슷해요.

    비유의 한계: 전기와 달리 GPU 처리량은 모델·최적화에 따라 몇 배씩 달라져요.

    조수(하루)

    처리량 슬라이더를 올리면 교차점이 왼쪽으로 가요. 같은 GPU에서 토큰을 더 뽑을수록 전용이 빨리 이득이 돼요 — 이게 2장부터의 최적화가 돈이 되는 이유예요.

    3칸

    1.2 우리 앱은 어떤 앱인가

    모델: 사용 사례가 정하는 설계교재: 1.2.1~1.2.3, 표

    연구실에서는

    농구 코치는 반에서 키 큰 학생을, 체조 코치는 작은 학생을 뽑아요. 같은 교실이라도 종목이 고르는 기준을 정합니다.

    모델에서는

    모든 추론 결정은 사용 사례에서 흘러나와요 원문. 범용 API나 추론 플랫폼을 만드는 게 아니라면, 사용 사례를 구체적으로 정해 제약을 최대한 더하는 편이 좋습니다.

    AI 네이티브 앱 여덟 가지 (교재 1.2.1 표)

    온라인과 오프라인 — 배치 크기 손잡이

    8
    용도

    풀이

    1. 추론 엔지니어링의 큰 거래 하나: 지연시간 vs 처리량. 지연이 낮으면 앱이 빠르고, 처리량이 높으면 같은 사용자 수를 GPU 더 적게 감당해 싸져요.
    2. 코드 완성·채팅·음성 에이전트는 사용자가 기다리는 온라인 앱 → 지연시간 우선. 팟캐스트 받아쓰기, 문서 정기 처리, 학습용 말뭉치 준비는 오프라인 일괄 작업 → 처리량 우선.
    3. 같은 모델(예: 음성 인식 Whisper)도 실시간 받아쓰기와 일괄 받아쓰기에 쓰일 수 있고, 양이 충분하면 배포를 둘로 나눠 각각 맞추는 편이 싸요.
    4. 소비자 앱은 비용에 민감하고 갑자기 몰리는 일이 잦아 한계 비용·유연성을, B2B는 마진이 좋고 사용이 안정적이지만 가용성·일정한 저지연을 우선합니다. 규제(데이터 주권, 개인정보, 법규 준수)는 둘 다 인프라 선택을 제한할 수 있어요.

    이 칸의 한계: 배치 곡선은 "배치를 키우면 각자는 기다리고 전체는 많이 한다"는 모양만 보여 줘요. 실제 모양은 GPU와 모델에 따라 다르며, 2장 2.4절(병목 계산)에서 원리를 봅니다.

    생성 AI로 치면

    같은 LLM이라도 채팅창(첫 토큰 빠르게)과 야간 문서 요약(처리량 최대)은 서로 다른 설정의 배포 두 개로 돌리는 게 보통이에요.

    비유의 한계: 규모가 작으면 둘로 나누는 운영 부담이 더 클 수 있어요.

    현장에 옮기면

    식당의 단품 주문(온라인)과 단체 도시락(오프라인)은 주방 동선을 다르게 짭니다.

    비유의 한계: 주방과 달리 GPU는 한 번에 처리하는 묶음이 커질수록 거의 공짜로 더 처리하는 구간이 있어요.

    초파리 연구원

    음성 통역에 처리량 최대 설정을 쓰면 말이 끊기겠네. 용도부터 정하라는 게 이 뜻이구나.

    1.3 모델 고르기 — 평가, 미세조정, 증류

    모델: 모델 선택교재: 1.3, 그림 1.2·1.3

    연구실에서는

    현미경 배율을 올릴수록 보이는 건 많지만 느리고 비싸요. "이 실험에 필요한 만큼"의 배율을 고르는 게 실력이에요.

    모델에서는

    다른 조건이 같다면, 파라미터가 적은 작은 모델의 추론이 더 빠르고 쌉니다. 그래서 모델 성능 최적화에서 가장 중요한 결정은 엔진도 추측 알고리즘도 아닌 어떤 모델을 고르느냐예요 원문.

    증류 — 선생 모델의 "확률 분포"를 보여 주면

    학생에게 보여 줄 것
    1

    풀이

    1. 초기 제품은 프런티어 모델의 토큰당 API를 쓰고, 규모를 키울 때는 반대로 — 일을 해낼 만큼 똑똑한 가장 작고 돌리기 쉬운 모델을 찾거나 만들라고 교재는 말해요. 인기 있는 모델 구조를 고르면 최적화 도구 지원도 넓어요.
    2. 평가(evals): 모델 지능을 체계적으로 재는 일. 빠르게 만들기 전에 쓸모를 확인하고, 품질을 떨어뜨릴 수 있는 최적화의 기준선이 됩니다. 공통 벤치마크는 후보를 추리는 데 쓰되 포화·조작될 수 있어요(굿하트의 법칙: 측정이 목표가 되면 좋은 측정이 아니게 된다).
    3. 미세조정: 사전학습 모델을 새 데이터로 특정 용도에 맞추기. 예: 자연어 → SQL은 범위가 좁아서 수십억 파라미터 정도의 작은 미세조정 모델이 같은 일에서 비슷한 성능을 낼 수 있어요.
    4. 증류: 큰 선생 모델로 작은 학생 모델을 학습시켜 행동을 흉내 내게 하기. 정답만이 아니라 선생의 확률 분포를 보여 줘요. 딥시크-R1(671B)의 라마·큐웬 기반 증류판이 대표 예예요.

    이 칸의 한계: 증류는 미세조정보다 실제로 덜 쓰인다고 교재는 말합니다. 그리고 선생의 좋은 점뿐 아니라 나쁜 버릇도 따라 배워요.

    생성 AI로 치면

    회사 SQL 도우미를 만든다면, 거대 범용 모델 대신 SQL만 잘하는 작은 미세조정 모델이 더 빠르고 쌀 수 있어요.

    비유의 한계: 모든 분야가 이만큼 작게 줄지는 않아요 — 교재도 "극단적인 예"라고 해요.

    현장에 옮기면

    신입에게 정답지만 주는 것(미세조정)과 선배의 판단 과정을 함께 보여 주는 것(증류)의 차이와 비슷해요.

    비유의 한계: 사람과 달리 모델은 선배의 실수도 그대로 흉내 냅니다.

    주판봇

    …큰 모델이 늘 정답은 아니라고? 작은 모델이 같은 점수면 GPU 값이 확 줄긴 하네.

    5칸

    1.4 지연시간과 처리량 재기

    모델: 지표교재: 1.4, 그림 1.4·1.5, 표

    연구실에서는

    실험 결과를 평균 하나로만 보고하면, 가끔 크게 튀는 값을 놓쳐요. 그래서 분포와 꼬리를 함께 봅니다.

    모델에서는

    LLM의 대표 지표는 TTFT(첫 토큰까지 시간)와 TPS(초당 토큰). 지연시간은 오른쪽으로 꼬리가 긴 분포라서 평균 대신 백분위(P50·P90·P95·P99)로 봅니다 원문.

    스트리밍 한 번 — TTFT · ITL · TPS

    400ms
    10ms
    100개
    체감 TPS = 1000 ÷ ITL(ms)  ·  ITL 10ms → 100 TPS 원문  ·  전체 응답 시간 = TTFT + (토큰 수 − 1) × ITL

    오른쪽 꼬리 분포와 백분위

    0.5
    재는 범위

    풀이

    1. TTFT는 계산이 몰리는 프리필에, TPS는 대역폭이 몰리는 디코드에 달려 있어요(2장에서 자세히). TTFT는 낮을수록, TPS는 높을수록 좋아요.
    2. TPS는 헷갈리는 말이에요: 체감 TPS(사용자 한 명이 받는 속도, 지연 지표)와 전체 TPS(서비스 전체가 내는 양, 처리량 지표). 토큰 사이 간격 ITL 10ms는 사용자당 100 TPS예요.
    3. 에이전트의 도구 호출처럼 토큰 하나하나가 쓸모없는 요청은 TTFT·TPS 대신 전체 응답 시간을 재요.
    4. 평균은 꼬리 때문에 P50보다 커지는 경우가 많아요(그림 1.5). P50은 둘에 하나, P90은 열에 하나, P95는 스물에 하나, P99는 백에 하나가 그보다 느리다는 뜻이에요.
    5. 추론 시간(GPU에서 토큰 만드는 시간)과 처음부터 끝까지(네트워크·대기열 포함)를 둘 다 보세요. 추론은 빠른데 전체가 느리면, 모델 최적화보다 인프라를 볼 때예요.

    이 칸의 한계: 표본은 설명용 로그정규 분포예요. 실제 서비스의 분포 모양은 부하·배치·요청 길이에 따라 달라요.

    생성 AI로 치면

    채팅 앱은 TTFT를, 긴 보고서 생성은 체감 TPS를, 에이전트는 전체 응답 시간을 먼저 봐요.

    비유의 한계: 사용자가 느끼는 속도에는 화면 그리기 같은 앱 쪽 시간도 섞여요.

    현장에 옮기면

    택배 평균 배송일이 이틀이어도, 열 번에 한 번 일주일 걸리면 고객은 그 한 번을 기억해요. P90·P99가 신뢰를 정합니다.

    비유의 한계: 택배와 달리 서버 꼬리는 몇 초 단위라 사용자가 금방 다시 누르고, 그게 또 부하가 돼요.

    초파리 연구원

    평균만 보면 열에 하나 몇 초씩 기다리는 사람을 못 봐. 그 사람이 다음 달에 떠나는 거야.

    VS판

    대결 — 평균이 낮은 쪽 vs P99가 낮은 쪽

    판정 기준: P99 응답 시간 (시드 고정 표본 각 1,000개)

    박사

    두 배포가 있어요. A는 평균이 더 낮고, B는 평균은 조금 높지만 꼬리가 짧아요. 1장이 권하는 대로 P99로 판정합니다.
